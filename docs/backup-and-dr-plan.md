# План резервного копирования и DR (вне основного провайдера)

Цель: обеспечить восстановление сервиса даже при проблемах основного облака/аккаунта (блокировка аккаунта, авария региона, случайное удаление ресурсов).

## 1. Принцип 3-2-1

- 3 копии данных:
  - рабочие прод-данные (основная инфраструктура),
  - резервная копия в основном провайдере,
  - резервная копия вне основного провайдера.
- 2 разных типа/локации хранения:
  - managed backup/snapshot,
  - объектное хранилище у второго провайдера.
- 1 off-provider копия обязательна (отдельный аккаунт или отдельный провайдер).

## 2. Что обязательно бэкапить

- PostgreSQL:
  - ежедневный полный бэкап,
  - WAL/PITR (если поддерживается),
  - хранение минимум 14-30 дней.
- Redis:
  - если данные Redis критичны для бизнеса, включить AOF/RDB и периодические выгрузки.
- Object Storage (файлы пользователей):
  - версионирование bucket,
  - lifecycle-политика и контроль удаления.
- Секреты и конфигурация:
  - безопасный экспорт секретов (в зашифрованном виде),
  - инфраструктурные манифесты (Terraform/Ansible),
  - env-шаблоны без секретов.

## 3. Рекомендуемая off-provider архитектура

Основной провайдер:
- Production: LB, App VM, PostgreSQL, Redis, object storage.

Внешний провайдер/аккаунт:
- backup bucket (только для резервных копий),
- доступ только у сервисной учетной записи backup-job,
- immutable/lock policy для критичных архивов (если доступно).

Поток:
1. Ночью делаем дамп БД (`pg_dump` или экспорт managed snapshot).
2. Архивируем метаданные релиза и конфигурационные артефакты.
3. Шифруем архив.
4. Загружаем во внешний backup bucket.
5. Проверяем checksum и сохраняем отчет.
6. Отправляем алерт при падении любого шага.

## 4. Минимальный baseline для этого проекта

- Бэкап БД:
  - daily full + PITR,
  - хранение 30 дней.
- Бэкап медиа:
  - репликация object storage или nightly delta sync во внешний bucket.
- Локация бэкапов:
  - отдельный облачный аккаунт (в идеале с отдельным владельцем биллинга),
  - отдельные credentials с write/read только в backup bucket.
- Шифрование:
  - at rest (шифрование bucket),
  - in transit (TLS),
  - опционально client-side шифрование перед загрузкой.

## 5. Расписание

- Ежедневно 02:00 UTC:
  - полный дамп БД + загрузка off-provider.
- Каждые 15 минут:
  - синхронизация WAL/PITR (если поддерживается managed БД).
- Ежедневно 03:00 UTC:
  - delta sync медиа.
- Еженедельно:
  - restore-тест на staging.
- Ежемесячно:
  - DR-учение "полная потеря основного провайдера".

## 6. Проверка восстановления (обязательно)

Еженедельный restore-тест:
1. Поднять временную БД.
2. Восстановить последний off-provider backup.
3. Прогнать smoke-тесты:
   - логин,
   - загрузка списка чатов,
   - отправка сообщения,
   - доступ к файлам.
4. Зафиксировать фактические RTO/RPO.

Целевые показатели:
- RPO: до 15 минут (с PITR), иначе до 24 часов (если только daily backup).
- RTO: 2-4 часа для базового восстановления.

## 7. Контроли безопасности бэкапов

- Не использовать root/admin credentials в backup-job.
- Ротация backup credentials минимум раз в 90 дней.
- MFA на аккаунт с доступом к backup bucket.
- Алерты на:
  - backup failure,
  - аномальный размер выгрузки,
  - checksum mismatch,
  - отсутствие свежего backup старше 24 часов.
- Хранить логи backup-job отдельно от логов приложения.

## 8. Аварийный runbook (основной провайдер недоступен)

1. Поднять чистую инфраструктуру у резервного провайдера.
2. Восстановить PostgreSQL из последнего off-provider backup.
3. Пересоздать Redis (или восстановить, если состояние критично).
4. Восстановить медиа из backup bucket.
5. Применить секреты из защищенного secret store.
6. Переключить DNS на новый LB.
7. Прогнать smoke-проверки и открыть трафик.
8. Оформить postmortem и список профилактических действий.

## 9. Зоны ответственности

- Owner: Backend/DevOps lead.
- Backup job owner: SRE/DevOps.
- DR drill owner: Tech lead.
- SLA коммуникации при инциденте: статус-апдейты каждые 30 минут.
