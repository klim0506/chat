# Архитектурное разнесение и защита «до конца»

Как развести компоненты по зонам и уровням, чтобы минимизировать поверхность атаки и изолировать данные.

Связанные документы: `ha-multi-vm-deployment.md` (отказоустойчивость), `server-security-and-stability.md` (firewall, секреты, мониторинг).

---

## 1. Уровни (ярусы) и кто куда ходит

Идея: **интернет не видит БД и Redis**. Только балансировщик/веб-сервер принимает трафик; приложение ходит во внутренние сервисы по внутренней сети.

```
                    Интернет
                         │
                         ▼
    ┌─────────────────────────────────────────────────────────┐
    │  Ярус 1: Edge (граница)                                  │
    │  • Load Balancer (или nginx)                             │
    │  • Опционально: WAF, DDoS-защита                         │
    │  Порт наружу: 80, 443. Внутрь — только на ярус 2.        │
    └───────────────────────────┬─────────────────────────────┘
                                 │
                                 ▼
    ┌─────────────────────────────────────────────────────────┐
    │  Ярус 2: Приложение (App / DMZ)                          │
    │  • nginx (статика + прокси к backend)                    │
    │  • Gunicorn + Daphne (Django)                            │
    │  Исходящие: только к ярусу 3 (БД, Redis). Не в интернет. │
    └───────────────────────────┬─────────────────────────────┘
                                 │
                    ┌────────────┴────────────┐
                    ▼                         ▼
    ┌───────────────────────────┐ ┌───────────────────────────┐
    │  Ярус 3: Данные            │ │  Ярус 3 (опционально)      │
    │  • PostgreSQL              │ │  • Celery workers          │
    │  • Redis                   │ │  Только из яруса 2,        │
    │  Никакого доступа из       │ │  подписываются на Redis.   │
    │  интернета. Только с       │ └───────────────────────────┘
    │  яруса 2 (и админки).      │
    └───────────────────────────┘
```

**Правило потоков:**

- Из интернета → только на ярус 1 (порты 80/443).
- Ярус 1 → только на ярус 2 (HTTP к nginx/app).
- Ярус 2 → ярус 3 (PostgreSQL, Redis). Ярус 2 не открыт в интернет напрямую (до него доходят только запросы через ярус 1).
- Ярус 3 не принимает соединения из интернета; firewall разрешает подключения только с яруса 2 (и при необходимости с отдельной «админской» подсети).

Так вы защищаетесь «до конца»: даже при уязвимости в приложении злоумышленник не сможет напрямую стучаться в БД или Redis с интернета — их просто нет в общем доступе.

## 2. Варианты размещения: от одной машины до трёх ярусов

### Вариант A: Всё на одной ВМ (текущая база)

| Компонент        | Где живёт      | Кто подключается        |
|------------------|----------------|--------------------------|
| nginx            | та же ВМ       | интернет (80/443)        |
| Gunicorn, Daphne | та же ВМ       | nginx (localhost)        |
| PostgreSQL       | та же ВМ       | приложение (localhost)   |
| Redis            | та же ВМ       | приложение, Celery       |
| Celery           | та же ВМ       | Redis (localhost)        |

**Защита:** firewall на ВМ: открыты только 22, 80, 443. Порты 5432 (PostgreSQL) и 6379 (Redis) **не** открывать наружу. Так вы уже разносите «логически»: снаружи доступны только веб и SSH.

### Вариант B: Две зоны — «фронт» и «данные»

- **ВМ 1 (фронт):** nginx, Gunicorn, Daphne, Celery. Открыты 80, 443. Подключается к ВМ 2 по внутренней сети.
- **ВМ 2 (данные):** PostgreSQL, Redis. Слушают только внутренний IP (или localhost + IP ВМ 1). Firewall на ВМ 2: разрешить 5432 и 6379 **только с IP ВМ 1** (и при необходимости с админской подсети).

Плюс: компрометация веб-сервера не даёт прямого доступа к БД с другой машины; пароли БД/Redis не лежат на «передней» машине в том же смысле, что и открытые порты (они всё равно в env приложения, но сетевой доступ к портам отрезан).

### Вариант C: Три яруса (Edge → App → Data)

- **Ярус 1 — Edge:** отдельная ВМ или облачный LB. Только TLS, балансировка, опционально WAF. Никакой БД и кода приложения.
- **Ярус 2 — App:** одна или несколько ВМ (nginx + Gunicorn + Daphne + опционально Celery). Доступ только с яруса 1 (по приватному IP или внутренней сети). К ярусу 3 подключаются по внутренней сети.
- **Ярус 3 — Data:** ВМ(и) с PostgreSQL и Redis. Порты 5432/6379 только с яруса 2 (и админки). Из интернета до яруса 3 трафик не доходит.

Так вы получаете чёткое разделение: edge только раздаёт трафик, приложение изолировано от интернета прямым доступом, данные доступны только приложению.

## 3. Сети и firewall между ярусами

Независимо от того, одна ВМ или несколько, важно зафиксировать **разрешённые направления** трафика.

### Одна ВМ (вариант A)

```text
Входящие: 22 (SSH), 80, 443. Всё остальное — deny.
Исходящие: по необходимости (apt, API SMS, YooKassa, Telegram и т.д.)
localhost: 5432, 6379 — только для процессов на этой же машине.
```

### Две ВМ: фронт и данные (вариант B)

**На ВМ «данные» (PostgreSQL, Redis):**

```bash
# Разрешить подключения только с IP фронт-сервера(ов)
sudo ufw allow from <IP_ВМ_ФРОНТ> to any port 5432
sudo ufw allow from <IP_ВМ_ФРОНТ> to any port 6379
sudo ufw deny 5432
sudo ufw deny 6379
# + разрешить SSH (с доверенного IP или везде, по политике)
sudo ufw enable
```

**На ВМ «фронт»:** как обычно — 22, 80, 443. Исходящие на ВМ данных по 5432/6379 — по умолчанию разрешены, если не запрещаете исходящие правилами.

### Три яруса (вариант C)

- **Edge:** входящие 80, 443; исходящие — только на приватные IP яруса 2 (порт 80/443 к nginx).
- **App:** входящие — только с IP Edge (и опционально админской подсети) на 80/443; исходящие — на ярус 3 (5432, 6379) и в интернет для внешних API (SMS, платежи и т.д.).
- **Data:** входящие — только с IP яруса 2 (и админки) на 5432, 6379; исходящие — по необходимости (обновления, репликация и т.д.).

Так вы «разводите» трафик по уровням и закрываете прямой доступ к данным из интернета.

## 4. Дополнительное разнесение по ролям

### Статика (frontend) отдельно от API

- **Сейчас:** nginx на app отдаёт и SPA, и проксирует `/api/` и `/ws/` на backend.
- **Вариант:** статику (HTML, JS, CSS) отдавать через CDN или отдельный домен/поддомен с другого сервера или хранилища (S3/Object Storage + CDN). На app-серверах nginx только проксирует API и WebSocket. Тогда компрометация кэша CDN не даёт доступа к backend; backend не отдаёт статику и может быть сильнее ограничен по заголовкам и путям.

### Celery на отдельных воркерах

- Celery можно вынести на отдельные ВМ (только worker’ы). Они подключаются к тому же Redis и той же БД, что и app, но не принимают HTTP. Плюсы: сбой или перегрузка воркеров не роняют веб; можно ограничить исходящие с этих ВМ (только Redis, БД и нужные API — SMS, платежи). Сеть для таких ВМ — та же «внутренняя» зона, что и app (доступ к Redis/БД).

### Платежи (webhook) и админка

- **Webhook YooKassa:** уже защищён по IP (`YOOKASSA_WEBHOOK_IP_ALLOWLIST`) и throttle. Архитектурно webhook принимает тот же app (nginx → backend). Дополнительно можно вынести webhook на отдельный endpoint/поддомен и на уровне nginx разрешать только IP YooKassa — так остальной API за ним не светится.
- **Django admin:** доступ только по VPN или с доверенных IP (nginx `allow`/`deny`), лучше не светить путь `/admin/` в поиске. Тогда админка остаётся в том же app-ярусе, но логически и по доступу отделена.

## 5. Защита «до конца» — чек-лист по ярусам

| Уровень        | Что сделать |
|----------------|-------------|
| **Интернет → Edge** | TLS 1.2+, сильные шифры; только 80/443; опционально WAF/DDoS-защита. |
| **Edge → App** | Трафик только на app-узлы (приватная сеть или внутренний LB); health check `/api/health/`. |
| **App**        | Нет прямого доступа в интернет к портам app (доступ только через Edge); nginx rate limit, admin по IP; секреты из env/Vault. |
| **App → Data** | Подключения к PostgreSQL и Redis только по внутренней сети; сильные пароли, при необходимости TLS между app и БД. |
| **Data**       | Порты 5432/6379 не видны из интернета; firewall только с app (и админки); бэкапы, шифрование дисков по политике. |

Плюс общие меры из `server-security-and-stability.md`: один и тот же SECRET_KEY на всех app-узлах, YooKassa allowlist, отключённый DEBUG, ротация логов и мониторинг.

## 6. Краткая схема «кто с кем говорит»

```text
Клиент (браузер)
    │ HTTPS
    ▼
[ Load Balancer / nginx ]  ← только 80/443, TLS
    │ HTTP (внутр. сеть)
    ▼
[ nginx + Gunicorn + Daphne ]  ← статика + /api/ + /ws/
    │
    ├──► PostgreSQL (внутр. сеть, порт 5432)
    ├──► Redis (внутр. сеть, порт 6379)
    └──► Внешние API (SMS, YooKassa, Telegram) по исходящему HTTPS

[ Celery workers ]  ← опционально те же ВМ или отдельные
    ├──► Redis (очередь)
    └──► PostgreSQL (результаты, данные)
```

Итог: архитектурно вы разносите **границу (edge)**, **приложение** и **данные**, и защищаете «до конца» тем, что БД и Redis нигде не открыты в интернет, а доступ к ним строго с яруса приложения (и при необходимости админской сети). Остальное — отказоустойчивость и масштабирование — см. `ha-multi-vm-deployment.md`.
