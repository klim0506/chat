|-------------|--------|------------|

## 2. Что можно убрать или не использовать

### 2.1. Приложение Tracking (меченые ссылки)

- **Таблицы:** `TrackingLink`, `TrackingLinkClick`.
- **Использование:** только админка (`/api/admin/tracking-links/`) и редирект `GET /t/<slug>/`. В основной логике чатов не участвует.
- **Рекомендация:** если меченые ссылки не нужны — приложение можно отключить: убрать `apps.tracking` из `INSTALLED_APPS`, убрать маршруты из `config/urls.py`. Таблицы тогда можно не создавать или удалить миграциями. Если нужны только «для будущего» — оставить как есть.

### 2.2. Группы и права Django (User.groups, user_permissions)

- **Таблицы:** `auth_group`, `auth_permission`, `users_user_groups`, `users_user_user_permissions`.
- **Использование:** админка (блок «Права»), в коде проверки только `is_staff` / `is_superuser`.
- **Рекомендация:** не удалять — без них ломается админка и `PermissionsMixin`. Если не используете группы в коде — просто не заводите группы; таблицы почти пустые и не мешают.

### 2.3. Поля User: telegram_id, telegram_username

- **Использование:** сериализаторы (профиль), админка, consumers (уведомления по @username).
- **Рекомендация:** оставить, если есть или планируется импорт из Telegram / привязка аккаунта. Если нет — можно со временем сделать nullable и не заполнять.

### 2.4. FileAttachment.storage_type (GOOGLE_DRIVE, MAILRU_CLOUD)

- **Использование:** в продакшене везде `LOCAL`; в тестах иногда другие типы.
- **Рекомендация:** если внешние хранилища не планируются — можно оставить один тип `LOCAL` и упростить код (убрать ветки по `storage_type` в задачах сканирования). Схему менять не обязательно.

### 2.5. PaymentLog.raw_response

- **Использование:** сохранение ответа ЮKassa, чтение `plan_months` при успешной оплате.
- **Рекомендация:** не убирать. При желании можно хранить только нужные поля (например, `plan_months`, `payment_id`), а не весь JSON — через отдельную миграцию и смену логики записи.

## 3. Оптимизация без удаления таблиц

### 3.1. Очистка использованных OneTimePreKey (E2EE)

- **Модель:** `e2ee.OneTimePreKey` (поля `device`, `key_id`, `is_used`).
- **Сделано:** добавлена задача Celery `apps.e2ee.tasks.purge_used_prekeys` — раз в сутки (4:00) удаляет все записи с `is_used=True`. Они больше не нужны для X3DH. Расписание в `config/celery.py`: `purge-used-prekeys`.

### 3.2. Очистка старых PaymentLog и StarTransaction

- Уже есть: задача `purge_old_idempotency_records` удаляет старые `PaymentLog` (терминальные статусы) и реферальные `StarTransaction` старше 30 дней. Проверьте, что задача включена в расписание Celery.

## 4. Реализовано: аналитика и источник регистрации

### 4.1. События аналитики

- **Сделано:** таблица `users.AnalyticsEvent` (user_id, event_type, payload JSONB, created_at), индекс по (event_type, created_at).
- Запись через `record_analytics_event(user, event_type, payload)`.
- События: **registration** (при первом входе по коду), **first_message** (при отправке первого сообщения пользователем). Админка: раздел «События аналитики».

### 4.2. Источник регистрации

- **Сделано:** у `User` добавлены поля `registration_source`, `utm_source`, `utm_medium`, `utm_campaign`.
- При верификации кода (`POST /api/auth/verify-code/`) в теле можно передать `ref`, `utm_source`, `utm_medium`, `utm_campaign`; для нового пользователя сохраняются в профиль и в событие `registration`.
- `registration_source` выставляется: `referral` (если был ref), `utm` (если передан любой utm_*), иначе `organic`.

### 4.3. Аналитика по чатам/каналам

- **Сейчас:** количество участников, сообщений, постов — считается по существующим таблицам.
- **Можно усилить:**
  - В разрезе по времени: агрегаты по дням (сообщений в день, новых участников в день) — через запросы к `Message`, `ChatMember`, `ChannelMember` с группировкой по дате.
  - Для скорости на больших объёмах — отдельная агрегирующая таблица (например, «статистика канала по дням») с фоновым пересчётом.

### 4.4. Доставка/прочтение сообщений

- **Сейчас:** факт «прочитано» выводится из `ChatMember.last_read_at` и времени сообщения.
- **Не хранится:** время первой доставки на устройство (для «доставлено»). Если нужно различать «доставлено» и «прочитано» с точным временем — можно добавить, например, таблицу `MessageDelivery` (message_id, user_id, delivered_at) или расширить события в `AnalyticsEvent`.

### 4.5. Поиск по сообщениям

- **Сейчас:** в настройках есть `django.contrib.postgres` (SearchVector).
- **Рекомендация:** если полнотекстовый поиск по сообщениям уже используется — убедиться, что есть индекс GIN по поисковому вектору. Если ещё не используется — при добавлении поиска заложить индекс при создании миграции.
