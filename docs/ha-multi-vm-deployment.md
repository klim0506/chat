# Отказоустойчивое размещение на группе виртуальных машин

Краткий план размещения PingyChat с отказоустойчивостью на нескольких ВМ: балансировщик, несколько инстансов приложения, HA для PostgreSQL и Redis.

Разнесение по зонам (DMZ, данные за firewall) и защита «до конца» — в [architecture-security-and-separation.md](architecture-security-and-separation.md).

**Как читать:** если незнакомы с терминами (балансировщик, Gunicorn, Patroni, Sentinel и т.д.) — сначала посмотрите раздел **«Пояснения: что за инструменты и термины»** после схемы архитектуры. В нём простыми словами расписано, что это за инструменты и зачем они нужны.

## Текущий стек (на одной машине)

| Компонент | Роль |
|-----------|------|
| **Frontend** | Статика (Vite build), nginx |
| **Backend** | Django (API + ASGI/Channels для WebSocket) |
| **PostgreSQL** | Основная БД |
| **Redis** | Кэш, Channel Layer (WebSocket), Celery broker |
| **Celery** | Фоновые задачи (OTP, платежи, purge и т.д.) |

## Пояснения: что за инструменты и термины

Ниже — коротко, «что это такое», чтобы было проще ориентироваться в документе.

### Балансировщик нагрузки (Load Balancer)

**Зачем:** Один входной адрес (домен или IP), а за ним несколько серверов с приложением. Балансировщик принимает запросы и **распределяет** их по этим серверам (по очереди, по загрузке или по другим правилам). Если один сервер упал — запросы перестают на него отправлять и идут только на оставшиеся. Так достигается отказоустойчивость на уровне приложения.

**Варианты:**
- **nginx** — веб-сервер и обратный прокси; можно настроить как балансировщик (проксировать на несколько `upstream`-серверов). Бесплатный, очень распространён.
- **HAProxy** — специализированный балансировщик (только распределение трафика, не раздача файлов). Часто используют для высокой нагрузки и тонкой настройки.
- **Облачный LB** (AWS ALB, Google Cloud Load Balancer, Yandex Cloud Load Balancer и т.п.) — сервис в облаке: вы поднимаете «балансировщик», привязываете к нему свои ВМ, HTTPS и проверки здоровья часто настраиваются в интерфейсе.

### Что стоит на каждой App VM

- **nginx** — отдаёт статику (HTML, JS, CSS фронта) и проксирует запросы к API/WebSocket на локальный Gunicorn/Daphne. То есть пользователь обращается к nginx, а nginx уже решает: отдать файл самому или передать запрос приложению.
- **Gunicorn** — сервер приложений для Django: запускает несколько процессов Python, которые обрабатывают обычные HTTP-запросы (GET/POST к API). Django сам по себе не «слушает» порт — его запускают через Gunicorn (или аналог).
- **Daphne** — сервер для ASGI (асинхронный интерфейс). В вашем проекте через него работают **WebSocket** (Django Channels). Gunicorn умеет только HTTP, WebSocket нужен отдельный процесс (Daphne).
- **Celery worker** — фоновый процесс, который забирает задачи из очереди (в Redis) и выполняет их: отправка SMS, обработка платежей, периодическая очистка данных и т.д. Можно запускать на тех же ВМ, что и веб-приложение, или вынести на отдельные машины.

### Health check (проверка здоровья)

Периодический запрос с балансировщика на каждый app-сервер (например `GET /api/health/` раз в 5 секунд). Если ответ не 200 или таймаут — узел считают «больным» и **временно снимают с балансировки**. Трафик на него не отправляют, пока проверка снова не начнёт проходить. Так балансировщик сам перестаёт слать запросы на упавшие или перегруженные машины.

### Sticky session (привязка к одному серверу)

По умолчанию балансировщик может каждый следующий запрос от одного пользователя отправить на другую ВМ. Для обычных запросов к API это нормально. Для **WebSocket** соединение долгоживущее: если после первого запроса следующий уйдёт на другую ВМ, соединение разорвётся. **Sticky session** — это правило: «запомнить», что этот пользователь (по cookie или по IP) уже ходит на сервер №2, и все его запросы продолжать отправлять на №2. Тогда WebSocket остаётся на одном сервере. Если сервер №2 упадёт — клиент переподключится уже к любому живому серверу.

### Primary и Replica (PostgreSQL)

- **Primary** (основной сервер) — единственный, кто принимает запись (INSERT, UPDATE, DELETE). Все приложения пишут только в него.
- **Replica** (реплика) — копия данных с primary в почти реальном времени (репликация). Обычно с реплики только **читают** (SELECT). Если primary падает, реплику можно **повысить** до нового primary (failover), тогда приложения переключают подключение на неё.

**Failover** — переключение с умершего primary на реплику, чтобы снова иметь один «главный» сервер для записи.

### Patroni, etcd, Consul (автоматизация PostgreSQL HA)

- **Patroni** — программа, которая управляет несколькими инстансами PostgreSQL: выбирает, кто сейчас primary, кто replica, и при падении primary автоматически назначает новым primary одну из реплик.
- **etcd** и **Consul** — хранилища ключ-значение с согласованием между узлами (consensus). Patroni использует их, чтобы несколько машин договорились, кто из них «лидер» (primary), без конфликтов. То есть Patroni + etcd/Consul дают автоматический failover без ручных скриптов.

### Redis: Master, Replica, Sentinel

- **Master** — один основной Redis, в него пишут и читают.
- **Replica** — копия данных с master (только чтение). Нужна для отказоустойчивости и иногда для разгрузки чтения.
- **Redis Sentinel** — отдельный процесс (обычно несколько на разных машинах), который следит за master и replicas. Если master падает, Sentinel **назначает** одну из реплик новым master. Приложение при подключении спрашивает у Sentinel: «где сейчас master?» — и получает актуальный адрес. Так вы не храните в коде жёстко один IP master, а получаете его динамически.

**Redis Cluster** — способ разнести данные по нескольким узлам (шардирование). Нужен при очень больших объёмах. Для кэша, очередей Celery и Channel Layer обычно хватает одного master + replicas + Sentinel.

### PgBouncer

Прокси между приложением и PostgreSQL. Принимает много соединений от приложения, а к самой БД держит меньше соединений (пул). Плюс можно настроить так, чтобы приложение подключалось к одному адресу (PgBouncer), а PgBouncer уже знает, куда слать запросы — на текущий primary. При failover меняют настройку только у PgBouncer, а не у всех app-серверов.

### Деплой и автоматизация

- **rsync** — утилита копирования файлов по сети (часто по SSH). Умеет копировать только изменившееся. В деплое: «скопировать собранный фронт и код бэкенда на каждую ВМ».
- **Ansible** — инструмент автоматизации: вы описываете «что сделать» (установить пакеты, скопировать файлы, перезапустить сервисы) в YAML-файлах (playbook), и Ansible выполняет это на списке серверов по SSH. Удобно для одинаковой настройки многих ВМ.
- **Terraform** — описание инфраструктуры в коде (какие ВМ, диски, сети создать в облаке). Часто используют вместе с Ansible: Terraform создаёт машины, Ansible их настраивает.
- **CI pipeline** (GitHub Actions, GitLab CI и т.д.) — сценарий, который запускается при пуше в репозиторий: собрать проект, прогнать тесты, задеплоить на сервер(а). Деплой на несколько узлов можно сделать шагом «для каждого хоста: rsync + перезапуск».

### Rolling restart (поочерёдный перезапуск)

Вместо «остановить все app-серверы → обновить → запустить все» делают так: обновили и перезапустили сервер 1 → проверили → сервер 2 → … → сервер N. В каждый момент часть серверов уже с новым кодом, часть ещё со старым. Балансировщик раздаёт трафик только на живые, поэтому пользователи почти не замечают обновления.

### Секреты (Vault, переменные окружения)

Пароли, ключи API, SECRET_KEY не должны лежать в коде или в открытом виде в репозитории. Их задают **вне** приложения:
- **Переменные окружения** — при запуске сервиса (systemd, Docker) передают `SECRET_KEY=...`, `DATABASE_URL=...`. В коде их читают через `os.environ` или через настройки Django.
- **HashiCorp Vault** и аналоги — отдельный сервис для хранения секретов; приложение при старте запрашивает у Vault нужные ключи. Удобно при большом количестве сервисов и строгих требованиях к ротации паролей.

### CDN (Content Delivery Network)

Сеть серверов по миру, которые отдают статику (картинки, JS, CSS) из точки, ближайшей к пользователю. Фронт можно положить в хранилище (S3, объектное хранилище) и раздавать через CDN, тогда с ваших ВМ статику можно не отдавать вообще или отдавать только как запасной вариант.

### Channel Layer (Django Channels)

Механизм, чтобы разные процессы Django (например на разных ВМ) могли обмениваться сообщениями для WebSocket. Сообщение «новое сообщение в чат» публикуется в общий слой (у вас — Redis). Все процессы, у которых открыты WebSocket-подключения для этого чата, получают это сообщение из Redis и отправляют его своим клиентам. Поэтому несколько app-серверов могут обслуживать один и тот же чат — они синхронизируются через Redis.

### Broker (очередь для Celery)

Celery не хранит задачи в памяти приложения — он кладёт их в **очередь** (broker). В вашем проекте это Redis: «сделай задачу X» записывается в Redis, любой Celery worker (на любой ВМ) может забрать задачу и выполнить. Все воркеры смотрят в один и тот же Redis — значит, одна общая очередь на всё приложение.

## 1. Уровень приложения (App VMs)

- На каждой ВМ: **nginx** (статика фронта + прокси к backend), **Gunicorn** (HTTP), **Daphne** (ASGI/WebSocket), опционально **Celery worker**.
- Один и тот же **SECRET_KEY** и **MESSAGE_ENCRYPTION_KEY** на всех инстансах (из секретов/CI, не из случайной генерации при деплое).
- **DATABASE_URL** и **REDIS_URL** указывают на общие (и при необходимости HA) сервисы БД/Redis.
- Статику фронта можно: раздавать с каждой ВМ (rsync/deploy на все узлы) или положить на общее хранилище / CDN.

Почему это уже отказоустойчиво по приложению: при падении одной ВМ балансировщик снимает её с проверок и трафик идёт на остальные.

## 2. WebSocket (Django Channels)

- Сейчас используется **Redis** как Channel Layer (`channels_redis`). Несколько инстансов Django подписываются на одни и те же каналы в Redis — сообщения доставляются на любой узел, где открыт нужный WebSocket. Дополнительная настройка не нужна.
- Рекомендация: на балансировщике включить **sticky session** (по cookie, например `route` или `SERVERID`), чтобы один и тот же клиент после первого handshake ходил на один и тот же app-сервер. Это уменьшает переподключения при рестартах; при падении узла клиент переподключится к другому и подпишется через Redis заново.

## 3. Сессии и JWT

- **Refresh-токен в httpOnly cookie** и **access в localStorage** не привязаны к конкретной ВМ — любой инстанс проверяет JWT по одному и тому же **SECRET_KEY**.
- Если используете Django session в БД — все инстансы пишут в одну PostgreSQL, сессии общие. Если session в Redis — общий Redis, тоже общие. Ничего менять не нужно.

## 4. PostgreSQL: отказоустойчивость

- **Минимум для HA:** один primary + один replica. Реплика только для чтения; при падении primary — переключение (failover) на replica (вручную или через Patroni/автоматику).
- **Подходы:**
  - **Ручной primary + standby:** настройка streaming replication, скрипт переключения при сбое.
  - **Patroni + etcd/Consul:** автоматический выбор leader и failover.
  - **Управляемый PostgreSQL** (облако): встроенный HA и автоматический failover.
- Приложение подключается к **одному** строке подключения (к текущему primary). После failover меняется DNS или endpoint в конфиге/секретах и перезапуск приложений (или использование PgBouncer/HAProxy перед PostgreSQL с проверкой живого primary).

## 5. Redis: отказоустойчивость

- **Redis Sentinel:** несколько инстансов Redis (master + replicas) + Sentinel для автоматического выбора master и переключения при сбое. Приложение подключается к Sentinel и получает адрес текущего master.
- **Redis Cluster:** для очень больших объёмов; для вашего сценария (кэш, channel layer, Celery) обычно достаточно **одного master + replicas + Sentinel**.
- В коде Django/Channels/Celery обычно задаётся один URL. Для Sentinel нужен либо URL вида `redis+sentinel://...`, либо отдельный конфиг (зависит от драйвера). Для начала можно поднять один Redis с persistence (AOF/RDB) и одной репликой, затем добавить Sentinel.

## 6. Celery

- Очередь в Redis (или в Redis HA). Воркеры могут работать на тех же App VMs или на отдельных ВМ — главное, чтобы все видели один и тот же broker (Redis). При падении одного воркера задачи подхватят другие.

## 7. Load Balancer

- **Варианты:** nginx на отдельной ВМ, HAProxy, облачный LB (AWS ALB, GCP LB, Yandex Cloud LB и т.д.).
- Обязательно: **health check** на HTTP (например, `GET /api/health/` или `GET /api/` с ожиданием 200). Снимать с балансировки узел при падении проверки.
- HTTPS лучше завершать на балансировщике (сертификаты в одном месте), до app-узлов — HTTP.

## 8. Деплой и конфигурация

- **Секреты:** SECRET_KEY, MESSAGE_ENCRYPTION_KEY, пароли БД/Redis — из внешнего хранилища (переменные окружения, vault, секреты оркестратора), не в репозитории.
- **Деплой на несколько app-узлов:** тот же `deploy-prod.sh` можно вызывать в цикле по списку хостов (rsync + ssh restart) или через Ansible/Terraform/CI pipeline.
- После деплоя поочерёдный перезапуск (rolling restart) уменьшает простой: обновить часть узлов → проверить → остальные.

## 9. Минимальный набор для старта

| Шаг | Действие |
|-----|----------|
| 1 | 2–3 App VM за балансировщиком, один и тот же код и env (кроме возможно DEBUG), общие SECRET_KEY и ключи шифрования. |
| 2 | Один PostgreSQL (пока без HA) — при желании позже добавить replica + Patroni. |
| 3 | Один Redis с persistence — при желании позже Redis + Sentinel. |
| 4 | Load Balancer с health check и sticky session (по cookie) для WebSocket. |
| 5 | Деплой: rsync статики и кода на все app-узлы, перезапуск сервисов (по одному узлу за раз). |

Так вы получаете отказоустойчивость на уровне приложения (при падении одной ВМ трафик уходит на другие). Дальше можно добавить HA для PostgreSQL и Redis по мере требований к доступности БД и кэша.

## 10. Проверочный список

- [ ] SECRET_KEY и MESSAGE_ENCRYPTION_KEY одинаковы на всех app-инстансах и не меняются при деплое.
- [ ] DATABASE_URL указывает на текущий primary PostgreSQL (или на PgBouncer/прокси при HA).
- [ ] REDIS_URL указывает на рабочий Redis (или на Sentinel при HA).
- [ ] Health check на балансировщике ведёт на живой backend (и при необходимости проверяет БД/Redis).
- [ ] Sticky session включён для уменьшения переподключений WebSocket.
- [ ] Бэкапы PostgreSQL и политика восстановления определены отдельно от HA.

Если нужно, можно вынести в отдельные файлы: пример конфига nginx для балансировщика, пример systemd units для нескольких узлов или docker-compose для локальной проверки мульти-ноды.
