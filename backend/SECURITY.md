# Безопасность

## Секреты и пароли (.env)

Пароль БД и другие секреты хранятся в **`backend/.env`**. Это обычная практика, если соблюдать правила:

1. **Файл не попадает в репозиторий** — в проекте `backend/.env` уже в `.gitignore`, в Git коммитится только `.env.example` (без реальных паролей).
2. **Локально:** не отдавайте `.env` никому и не копируйте в облако/чаты. Для разработки на своём ноуте этого достаточно.
3. **На сервере (прод):**
   - Ограничьте доступ к файлу: `chmod 600 backend/.env` (читает только владелец).
   - Лучше не класть пароль прямо в файл на диске, а передавать через **переменные окружения** при запуске (systemd, Docker, CI): тогда в `.env` на проде можно оставить пустой `DATABASE_URL`, а значение задать в `Environment=` или в Docker `environment`.
   - Для максимальной изоляции используйте **секреты** провайдера: Docker Secrets, Kubernetes Secrets, Yandex Lockbox, AWS Secrets Manager и т.п. — приложение получает пароль при старте из сервиса, а не из файла.

**Итог:** хранить пароль в `.env` безопасно при условии, что файл не в Git и доступ к нему ограничен. В проде предпочтительно подставлять секреты через переменные окружения или менеджер секретов.

### Если сервер взломают — .env прочитают

Если злоумышленник получит доступ к серверу (SSH, уязвимость в приложении, утечка бэкапа), он сможет прочитать и `.env`, и переменные окружения процесса. То есть **сам по себе перенос пароля из .env в переменные окружения от взлома сервера не спасает** — секреты всё равно в памяти/на диске.

Что реально снижает риски:

- **Ограничение доступа к серверу:** только по SSH с ключами, firewall, минимум открытых портов, обновления.
- **Права на файл:** `chmod 600 backend/.env`, владелец — пользователь, от которого крутится приложение (не root в идеале).
- **Веб-сервер не отдаёт .env:** nginx/apache не должны отдавать файлы из каталога с `.env` (в проекте статика вынесена, но проверьте конфиг).
- **Менеджер секретов (Vault, облако):** пароль БД хранится не на сервере, приложение при старте запрашивает его по токену. Тогда при компрометации сервера на диске нет пароля БД — но токен доступа к хранилищу секретов всё равно нужно хранить (в .env или env), так что полной защиты нет, лишь усложнение для атакующего и централизованный учёт/ротация.

Вывод: `.env` на сервере не «взламывают» отдельно — взламывают **сервер**. Задача — не дать доступ к серверу и минимизировать ущерб (отдельный пользователь, бэкапы без .env, ротация паролей после инцидента).

## Защита сервера (VPS)

Ниже — базовый чеклист для Linux-сервера (Ubuntu/Debian), на котором крутится приложение. Выполнять по порядку, после каждого шага проверять, что вход по SSH и работа сервисов не сломались.

### 1. Вход по SSH только по ключам

- На своём ПК сгенерировать ключ (если ещё нет): `ssh-keygen -t ed25519 -C "your@email"`.
- Скопировать публичный ключ на сервер: `ssh-copy-id root@IP_СЕРВЕРА` (или `cat ~/.ssh/id_ed25519.pub` и вручную добавить в `~/.ssh/authorized_keys` на сервере).
- Зайти на сервер по ключу и **отключить вход по паролю**:
  ```bash
  sudo nano /etc/ssh/sshd_config
  ```
  Выставить: `PasswordAuthentication no`, `PermitRootLogin prohibit-password` (или `PermitRootLogin no` и заходить под обычным пользователем с sudo). Сохранить, перезапустить SSH: `sudo systemctl restart sshd`. **Не закрывать сессию** — открыть новый терминал и проверить вход по ключу. Только после успешной проверки закрывать старую сессию.

### 2. Файрвол — открыты только нужные порты

Разрешить только SSH (22), HTTP (80), HTTPS (443). Всё остальное закрыть.

```bash
sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status
```

Если SSH слушает на другом порту — указать его вместо 22. После `ufw enable` убедиться, что новый SSH-вход работает.

### 3. Автообновления безопасности

Установить автоматические обновления безопасности пакетов:

```bash
sudo apt update && sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
```

При желании настроить в `/etc/apt/apt.conf.d/50unattended-upgrades` перезагрузку только при необходимости (`Unattended-Upgrade::Automatic-Reboot "false"` или `"true"` с указанием времени).

### 4. Защита от перебора паролей (fail2ban)

Если вдруг пароль для SSH ещё где-то включён или есть другие сервисы с логином — ограничить число попыток:

```bash
sudo apt install -y fail2ban
sudo systemctl enable fail2ban
sudo systemctl start fail2ban
```

По умолчанию jail для SSH уже обычно включён. Статус: `sudo fail2ban-client status sshd`.

### 5. Отдельный пользователь для приложения

Не крутить приложение от root. Создать пользователя, например `app`:

```bash
sudo adduser app
sudo usermod -aG docker app   # если приложение в Docker
```

Файлы проекта и `.env` должны принадлежать этому пользователю; сервисы (systemd или Docker) запускать от него. Тогда при компрометации приложения злоумышленник не получит сразу root.

### 6. Минимум сервисов

Отключить и остановить всё лишнее (например, старые веб-серверы, неиспользуемые демоны): `sudo systemctl list-unit-files --type=service`, отключить ненужное: `sudo systemctl disable --now имя_сервиса`.

### 7. Nginx не отдаёт служебные файлы

В конфиге nginx не должно быть `root` или `alias` на каталог, где лежит `backend/.env` или исходники. Статика — только из выделенной директории (например `frontend/dist/`, `backend/staticfiles/`). Проверить: запрос к `https://ваш-домен/.env` должен возвращать 404 или 403.

**ALLOWED_HOSTS в проде:** задайте только реальные домены (например `pingychat.com,www.pingychat.com,web.pingychat.com`), без `*`. Иначе возможна подмена Host и обход проверок.

**Django Admin:** если админка доступна по HTTP (например через `location /admin/` с proxy_pass на бэкенд), ограничьте доступ по IP в nginx: `allow ваш_офисный_ip; deny all;` внутри соответствующего `location`, или используйте fail2ban (jail nginx-http-auth).

### 8. База данных не в интернет

PostgreSQL и Redis должны слушать только `127.0.0.1` (localhost) или внутреннюю сеть Docker, **не** 0.0.0.0. Доступ извне закрыт файрволом (п. 2) и привязкой к localhost. Если БД в Docker — не пробрасывать порты 5432/6379 наружу без необходимости.

### 9. Резюме

| Что сделать | Зачем |
|-------------|--------|
| SSH только по ключам, пароль отключить | Исключить подбор пароля по SSH |
| UFW: 22, 80, 443 | Остальные порты недоступны снаружи |
| unattended-upgrades | Закрывать известные уязвимости в пакетах |
| fail2ban | Ограничить перебор по SSH и др. |
| Отдельный пользователь для приложения | Ограничить ущерб при взломе приложения |
| Nginx не отдаёт .env и каталоги с секретами | Секреты не утекут через веб |
| PostgreSQL/Redis только localhost | БД недоступна из интернета |

После изменений всегда проверять вход по SSH в новом окне перед закрытием текущей сессии.

## Защита от DDoS и перегрузки

**Чем опасны DDoS-атаки для приложения:** массовые запросы могут исчерпать соединения nginx/backend, перегрузить CPU и память, исчерпать канал — в результате сайт станет недоступен для обычных пользователей. Для чата особенно чувствительны API и WebSocket.

**Что уже сделано на уровне nginx:**

| Мера | Назначение |
|------|------------|
| **limit_req** на `/api/` | Не более 30 запросов/сек с одного IP (burst 50). Снижает флуд запросами к API. |
| **limit_req** на `/admin/` | 5 запросов/мин с IP — защита от перебора пароля админки. |
| **limit_conn** на весь сервер | Не более 40 одновременных соединений с одного IP. Один источник не может занять все воркеры. |

Зоны заданы в `docker/nginx/conf.d/pingychat-limit-req.conf`, подключаются в конфиге сайта. При превышении лимита nginx возвращает 503.

**Что можно сделать дополнительно:**

1. **Cloudflare (или аналог)** — поставить домен за прокси (оранжевое облако). Часть атаки отфильтруется на краю сети (в т.ч. объёмные L3/L4 атаки), до сервера дойдёт меньше трафика. Бесплатный тариф часто достаточен для средних нагрузок.
2. **Ограничение по гео** — если аудитория только РФ/СНГ, в nginx или в Cloudflare можно ограничить доступ с других регионов (снижение ботнет-трафика из других стран).
3. **Масштабирование** — при росте нагрузки: больше воркеров backend, отдельный сервер для статики, балансировщик. Лимиты в nginx при этом можно ослабить (увеличить rate/conn), но не убирать.

**Ограничение:** лимиты по IP легко обходятся распределённой атакой (много разных IP). Поэтому для серьёзной защиты от больших DDoS нужен именно внешний сервис (Cloudflare, AWS Shield, провайдер хостинга с анти-DDoS).

**Итог:** на одном сервере мы защищаемся от перегрузки одним/несколькими злоумышленниками (флуд, исчерпание соединений). От мощной распределённой атаки лучше защищаться на уровне CDN/провайдера.

## Аудит зависимостей

Рекомендуется периодически проверять зависимости на известные уязвимости.

### Backend (Python)

```bash
cd backend
pip install pip-audit
pip-audit
```

Исправление: обновить пакеты в `requirements.txt` и переустановить зависимости. При необходимости использовать `pip-audit -r requirements.txt --fix`.

### Frontend (Node)

```bash
cd frontend
npm audit
npm audit fix   # по возможности автоматическое обновление
```

## Тесты безопасности

Регрессионные тесты по безопасности находятся в приложениях:

- **apps.users.tests_security** — JWT (refresh не принимается как access), rate limit для auth
- **apps.files.tests_security** — токен доступа к файлам (срок действия, подпись), обязательная авторизация загрузки
- **apps.payments.tests_security** — webhook (валюта/сумма, идемпотентность), валидация return_url

Запуск всех тестов:

```bash
cd backend
python manage.py test apps.users.tests_security apps.files.tests_security apps.payments.tests_security apps.chats.tests
```

## Rate limiting

- **send-code**: 5 запросов/мин с IP
- **verify-code**: 15 запросов/мин с IP
- **refresh**: 30 запросов/мин с IP
- **payments/webhook**: 60 запросов/мин с IP

Лимиты задаются в `config.settings.base.REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"]`. Для работы throttle при наличии Redis используется кэш (Redis); без Redis — локальная память (LimMemCache).
